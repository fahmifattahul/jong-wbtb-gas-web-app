BAB 1 — PENDAHULUAN
1.1 Latar Belakang
Kabupaten Lingga memiliki kekayaan Warisan Budaya Takbenda (WBTb) yang signifikan, mulai dari tradisi lisan, seni pertunjukan, adat istiadat, hingga kemahiran kerajinan tradisional. Namun, proses pengusulan WBTb ke tingkat nasional selama ini menghadapi beberapa kendala mendasar:
Dokumen formulir usulan, kajian akademik, dan file multimedia tersebar di berbagai perangkat lokal tanpa struktur direktori yang baku.
Terjadi tumpang-tindih penyuntingan dokumen antara Tim Pengusul dengan verifikator internal dinas, serta ketidakjelasan versi dokumen terbaru.
Tidak ada mekanisme tracking status pengusulan yang transparan dan terpusat.
Pembangunan sistem berbasis server mandiri membutuhkan anggaran besar yang tidak tersedia di APBD daerah.
1.2 Tujuan Sistem
JONG WBTb dibangun untuk mencapai tujuan berikut:
Mengdigitalisasi alur kerja pengusulan WBTb dari draf mentah hingga penetapan sertifikat nasional.
Menyediakan ruang kerja digital terpusat berbasis Google Workspace tanpa biaya infrastruktur tambahan.
Menerapkan kontrol versi dokumen yang ketat sesuai standar Juknis Tata Kelola Dokumen Digital WBTb 2026 Revisi 2.
Memastikan kepatuhan terhadap Juknis dalam setiap alur kerja sistem.
1.3 Ruang Lingkup
Sistem JONG WBTb mencakup:
Manajemen Folder Usulan — dari inisiasi hingga penetapan final atau penangguhan.
Workspace kolaboratif — pengelolaan formulir (Google Docs), kajian ilmiah (PDF), foto, dan video.
State machine pengusulan — 6 status resmi sesuai Juknis Bab VIII huruf D.
Manajemen hak akses berbasis peran (RBAC) — Atasan, Operator, Anggota Tim.
Audit trail — seluruh aktivitas tercatat di log terpusat.
Arsip historis — import WBTb yang telah ditetapkan sebelum Juknis berlaku.
Sistem ini TIDAK mencakup: hosting video mandiri, sistem keuangan/pendanaan, dan portal informasi publik terbuka.

2.3 Prinsip Desain
Zero-cost infrastructure — seluruh komponen memanfaatkan layanan Google gratis atau yang sudah tersedia di instansi.
Concurrency control — semua operasi tulis ke Google Sheets dilindungi LockService.getScriptLock() dengan timeout 30 detik untuk mencegah race condition.
Separation of concerns — setiap modul GAS memiliki tanggung jawab tunggal yang terdefinisi dengan jelas.
Juknis-first design — setiap keputusan arsitektur mengacu pada ketentuan Juknis sebagai governing constraint.

4.5 Aturan Putaran Revisi
Putaran Revisi (P01, P02, ...) hanya dapat dibuka dengan syarat:
Catatan Penilai Eksternal dari Provinsi atau Kementerian telah diterima secara resmi oleh Atasan.
Operator mendokumentasikan catatan tersebut di sistem via fungsi entryCatatanPenilai().
Sistem otomatis membuat subfolder P01/, P02/, dst. di 03_REVISI/.
Putaran Revisi TIDAK dapat dibuka oleh keputusan Atasan internal — ini sepenuhnya domain penilai eksternal. (Juknis Bab VI huruf D)

6.2 Aturan Pengembangan
Selalu gunakan konstanta COL.* untuk akses kolom sheet — jangan hardcode index angka.
Semua operasi tulis ke sheet harus lewat DatabaseEngine.executeTransaction() — tidak boleh bypass untuk mencegah race condition.
changeStatus() adalah satu-satunya pintu perubahan status — tidak ada kode lain yang boleh langsung set nilai kolom status.
namaFile() adalah satu-satunya fungsi penamaan file — tidak ada hardcode nama file di tempat lain.
Setiap operasi arsip harus diikuti updateFileMetadata() untuk menjaga sinkronisasi Drive dan database.
Status DIPERBAIKI hanya boleh dibuka via entryCatatanPenilai() — tidak via changeStatus() langsung.

7.3 Alur Penetapan Operator
Sesuai Juknis Bab II huruf B — Operator ditetapkan secara tertulis oleh Atasan:
Atasan login ke sistem → menu Administrasi → Tetapkan Operator Baru.
Pilih Anggota Tim yang akan dijadikan Operator → isi catatan (opsional).
Sistem generate Surat Penetapan Operator dalam format PDF otomatis.
PDF tersimpan di JONG_WBTB_ADMINISTRASI/PENETAPAN_OPERATOR/ di Google Drive.
Role Anggota Tim yang dipilih otomatis berubah menjadi Operator di db_users.
Operator lama (jika ada) dicabut aksesnya secara otomatis.
7.4 Alur Perintah Akses Tertulis
Sesuai Juknis Bab II huruf C — setiap perubahan akses harus atas perintah tertulis Atasan:
Atasan menu Administrasi → Terbitkan Perintah Akses Tertulis.
Isi tindakan (TAMBAH/CABUT), email, nama, role, dan alasan.
Sistem generate dokumen Perintah Akses PDF → tersimpan di Drive administrasi.
Operator menerima instruksi → eksekusi via menu Kelola Akses.
Batas waktu eksekusi: paling lambat 1 (satu) hari kerja sejak perintah diterima. (Juknis Bab II huruf C)
7.5 Retensi Arsip Ditangguhkan
Sesuai Juknis Bab IV huruf E:
Dokumen di subfolder 05_ARSIP-DITANGGUHKAN boleh dihapus Operator setelah retensi 1 (satu) tahun sejak tanggal penetapan status Ditangguhkan.
&apos;Boleh&apos; — bukan kewajiban. Keputusan sepenuhnya di tangan Operator.
Sistem mengirim notifikasi email ke Operator setiap tanggal 1 tiap bulan via time-driven trigger GAS.
Notifikasi mencakup folder yang sudah melampaui 1 tahun dan folder yang dalam 30 hari akan melampaui retensi.
Setiap penghapusan wajib dilaporkan ke Atasan via email otomatis.
Penghapusan memindahkan file ke Google Drive Trash (bukan permanent delete) — safety net 30 hari.

8.3 Sistem Routing
Routing berbasis fungsi JavaScript — tidak ada page reload. Navigasi memanggil fungsi render yang sesuai:
navigateTo(&apos;dashboard&apos;)   → renderDashboard()
navigateTo(&apos;workspace&apos;)   → renderWorkspace()
navigateTo(&apos;verifikasi&apos;)  → renderVerifikasi()
// dst...
8.4 GAS Communication Pattern
Semua panggilan ke server GAS menggunakan wrapper Promise untuk menghindari callback hell:
async function renderDashboard() {
  const data = await gasCall(&apos;getDashboardData&apos;, App.user.email);
  renderMetrics(data.metrics);
}
8.5 App State
State aplikasi disimpan di objek global App:
const App = {
  user: { email, nama, role },    // data pengguna aktif
  currentPage: &apos;dashboard&apos;,       // halaman aktif
  data: { proposals, arsip, ... } // cache data per sesi
};

9.3 Pengaturan Deploy Kritis
Setting yang WAJIB benar saat deploy Web App:
Setting
Nilai yang Benar
Konsekuensi Jika Salah
Execute as
User accessing the web app
Jika &quot;Me&quot;, semua user terdeteksi sebagai email deployer — RBAC tidak bekerja.
Who has access
Anyone with Google account
Jika &quot;Anyone&quot;, user tidak perlu login — RBAC bypass. Jika &quot;Only myself&quot;, hanya deployer yang bisa akses.
9.4 Update Kode Setelah Produksi
Setiap perubahan kode GAS TIDAK otomatis aktif di deployment. Langkah update:
Edit kode di GAS editor.
Deploy → Manage deployments → klik ikon pensil (edit) di deployment aktif.
Di dropdown Version → pilih New version.
Klik Deploy.
JANGAN klik &apos;New deployment&apos; — akan generate URL baru yang berbeda dari yang sudah dibagikan ke pengguna.

Masalah
Kemungkinan Penyebab
Solusi
Akses Ditolak saat login
Email tidak ada di db_users atau kolom aktif bukan TRUE
Cek sheet db_users. Pastikan email persis sama dan aktif = TRUE (boolean).
Loading screen tidak selesai
Error JavaScript di frontend
Buka DevTools → Console → cek error. Sering karena template literal backtick dalam string URL.
Error &quot;Database sedang sibuk&quot;

Tunggu beberapa detik dan coba lagi. Terjadi jika banyak user submit bersamaan.
Perubahan kode tidak efektif
Deployment belum diupdate
Deploy → Manage deployments → edit → New version → Deploy.
Cache role tidak update
CacheService TTL 5 menit belum habis
Jalankan clearCache() di GAS editor atau tunggu 5 menit.
